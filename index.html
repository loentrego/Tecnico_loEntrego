01

Arquitectura

La gente entra al dominio (loentrego.com, en Namecheap), que apunta al VPS de Bluehost. Ahí Nginx sirve los cuatro frontends y la API, y la API es la única que habla con la base de datos. GitHub no atiende usuarios: guarda el código, despliega al VPS con GitHub Actions y publica en Pages un mockup con datos ficticios.

Prender y apagar el mantenimiento

# La AppWeb muestra "Volvemos pronto" (la web y el admin siguen normales)
touch /srv/loentrego/mantenimiento/app.on

# Vuelve a la normalidad
rm /srv/loentrego/mantenimiento/app.on

# Igual para los otros sitios: web.on · admin.on

No hay que tocar código ni reiniciar nada: Nginx responde 503 con la página de mantenimiento mientras exista el archivo. Probado con los cuatro frontends reales.

Todo en el dominio

Frontends y API viven en el VPS, bajo loentrego.com. GitHub guarda y despliega; Pages solo muestra el mockup.

Una sola puerta

Solo la API toca la base. Postgres y Redis escuchan en localhost; desde internet solo se ven los puertos 80 y 443.

Reglas en la base

El flujo del pedido, la autoasignación por zona y el historial viven en Postgres. Ningún cliente se las puede saltar.

02

Programas del VPS

Todo se instala con un solo script: vps/instalar.sh. Es idempotente, así que se puede volver a correr sin romper nada.

En Bluehost: al crear o reinstalar el VPS, elige Ubuntu sin panel (self-managed). Si viene con AlmaLinux o cPanel, se reinstala desde el panel de Bluehost antes de correr el script. El script instala PostgreSQL 16 desde el repositorio oficial de PostgreSQL, así que funciona igual en Ubuntu 22.04 y 24.04.

Instalar

# 1. Namecheap → Domain List → loentrego.com → Advanced DNS → 4 registros A,
#    todos con valor = IP del VPS de Bluehost:   @   www   app   admin
# 2. Copiar la carpeta vps/ al servidor y correr como root:
DOMINIO=loentrego.com CORREO=contacto@loentrego.com bash vps/instalar.sh

# 3. Pegar la llave pública de GitHub Actions para el usuario "despliegue"
nano /home/despliegue/.ssh/authorized_keys
#    y en cada repo de frontend: github/desplegar-frontend.yml → .github/workflows/

# 4. Crear las tablas y los datos iniciales
source /srv/loentrego/.env
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f db/esquema.sql
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f db/semilla.sql

# 5. Comprobar
curl -I https://loentrego.com
curl -I https://app.loentrego.com/api/salud

El script crea el usuario loentrego (sin acceso root), la base, una clave aleatoria en /srv/loentrego/.env, el usuario despliegue con sus carpetas, el servicio de la API, los tres sitios de Nginx con HTTPS (un certificado para @, www, app y admin) y el respaldo diario.

05

Entradas y salidas

Todos los campos y botones de los frontends (web, AppWeb, panel, links y mantenimiento), hasta el más pequeño. Para cada uno: qué dato toma, qué regla cumple y a qué llamada de la API va. Cada llamada trae el JSON exacto que se envía y el que se recibe.

Diagrama general

Cómo leer cada pantalla

Diagrama de secuencia

De izquierda a derecha: la pantalla pide a la API, la API consulta la base y la respuesta vuelve. Un número por llamada.

Campos y botones

Cada control con su campo JSON y su regla. En el navegador no llama a la API; Abre otra app abre WhatsApp, el teléfono, el correo o Maps.

Envía y recibe

El JSON de ejemplo y, debajo, campo por campo con su tipo. Las estructuras que se repiten están al final.

Reglas comunes

  • Formato: todo va y vuelve en JSON (Content-Type: application/json), salvo las fotos (multipart) y la guía (PDF).
  • Sesión: las rutas con "Token" llevan Authorization: Bearer <token>. Si la API responde 401, el frontend pide uno nuevo con POST /api/refrescar y repite la llamada.
  • Dinero en pesos enteros (45000); el frontend lo muestra como $45.000. Celulares solo dígitos (3001234567); se muestran 300 123 4567.
  • Fechas en ISO 8601 con zona de Colombia (2026-11-23T09:40:00-05:00).
  • Errores siempre con la misma forma (Error); con 422 llega campos para marcar cada campo en rojo.
  • Real y mockup: en el dominio (loentrego.com, app., admin.) todo pasa por estas llamadas. En GitHub Pages el mockup usa datos ficticios y los usuarios demo, sin API. En producción, los usuarios demo tienen que quedar apagados.
  • Lo que hoy es local (zonas en localStorage, territorio.json, ESTADO de mantenimiento, usuarios demo) pasa a estas llamadas cuando exista el backend, sin cambiar las pantallas.

06

Base de datos

PostgreSQL 16 con PostGIS. Un solo esquema guarda todo el ecosistema, organizado en 10 áreas. El archivo completo, probado en una base real, está en db/esquema.sql.

Convenciones

  • Nombres en español, en minúscula y con guion bajo: pedido_eventos, zona_id.
  • Llaves: uuid en casi todo. Los catálogos que ya usan los frontends llevan texto estable (municipios.id = 'bogota', zonas_reparto.id).
  • Dinero en pesos, como entero (bigint): el peso colombiano no usa centavos.
  • Fechas con zona horaria (timestamptz); la operación es en America/Bogota.
  • Mapas en WGS84 (SRID 4326): puntos como geography, polígonos como geometry con índice GIST.
  • No se borra: lo que se quita en la app se archiva (archivado_en). El historial y la auditoría se conservan.

Lo que hace la base sola

Al crear un pedido

Pone la tarifa vigente del municipio, la localidad y la zona según el punto, y sugiere el repartidor de la zona con menos pedidos activos (y jornada abierta). Si la dirección cae en un hueco, usa la zona más cercana y marca fuera_de_zona.

Al cambiar de estado

Solo deja avanzar en orden: Por recoger → Recogido → En camino → Entregado, o No entregado con motivo. Un pedido cerrado no se reabre.

Historial automático

Cada cambio de estado queda en pedido_eventos con hora y usuario, y cada cambio de repartidor en asignaciones (automático, manual o por intercambio).

Cálculos guardados

La diferencia del cierre de caja, el neto de cada liquidación y el total del pago al repartidor se calculan en la base (GENERATED). Nadie los escribe a mano.

09

Respaldo y seguridad

Respaldos

Copia completa de la base cada día a las 3:15 a. m. (vps/respaldo.sh). Se guardan 14 días en el servidor y una copia cifrada en R2/B2. Probar una restauración una vez al mes.

Claves y llaves

Las claves de los usuarios se guardan con hash (bcrypt o argon2), nunca en texto. Las llaves de servicios viven en .env con permisos 600, fuera de Git.

Acceso al servidor

SSH solo con llave, sin root ni clave. Firewall con 22, 80 y 443. Postgres y Redis no se exponen. fail2ban bloquea intentos repetidos.

Inicio de sesión

Nginx limita a 10 intentos por minuto por IP en /api/login, y la base registra cada intento en intentos_ingreso.

Datos personales

Nombres, celulares y direcciones de clientes finales son datos personales (Ley 1581 de 2012). Solo se usan para la entrega, y el panel no rastrea la ubicación de los repartidores.

Auditoría

Cambios sensibles (zonas, tarifas, liquidaciones, usuarios) quedan en auditoria con el antes, el después, quién y desde qué IP.
